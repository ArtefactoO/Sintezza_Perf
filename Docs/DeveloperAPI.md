# Подключение к Sintezza_Perf API v1

Этот контракт предназначен автору аддона. Perf уже содержит регистрацию, ограниченный сбор, отчеты и интерфейс. Интеграция Sintezza_UI выполняется отдельной задачей: производственный Perf не регистрирует за него вымышленные модули и не меняет его функции.

Публичная точка входа: **`_G.Sintezza_PerfAPI`**, поле **`version == 1`**. Это версия контракта API, независимая от версии аддона `0.7.0`. Все методы ниже вызываются через двоеточие. Внутренний namespace Perf и функции `ns.Dev*` не являются публичным API.

## Быстрый путь для Sintezza_UI

1. В существующей строке `## OptionalDeps:` TOC Sintezza_UI добавьте `Sintezza_Perf`, сохранив другие зависимости. Не делайте его обязательной зависимостью. Не добавляйте обратную зависимость Sintezza_UI в TOC Perf.
2. Загрузите собственный `PerfBridge.lua` до файлов, которые будут пользоваться адаптером. Сохраните существующий namespace и порядок инициализации UI.
3. Зарегистрируйте один модуль карты и две-три конкретные операции. Начните со счетчиков и одной синхронной дорогой операции. Создавайте обертки один раз при загрузке, после определения исходной функции.
4. Передайте начальную видимость окна и обновляйте ее в уже существующих обработчиках состояния. Сигнал изменения передавайте только там, где известно, что изменились данные.
5. Откройте `/sperf dev`, выберите модуль и выполните короткий замер. Затем проверьте оба пути без Perf и с выключенной записью.

Perf устанавливается как обычный аддон. Общие CPU/память во вкладке «Нагрузка» доступны без этой интеграции. Чтобы получить разбивку на модули и функции, точки должен добавить владелец измеряемого кода.

### Готовый каркас адаптера

Это код **для будущей доработки Sintezza_UI**, его не нужно помещать в Sintezza_Perf. Имена локальных функций и точек согласуйте с реальной архитектурой UI. `title` обязателен как английский fallback; `titleRu` используется при русском языке темы. Идентификаторы от языка не зависят.

```lua
-- PerfBridge.lua, загружается один раз в составе Sintezza_UI.
local addonName, ns = ...
local Bridge = {}
ns.PerfBridge = Bridge

local api = _G.Sintezza_PerfAPI
if type(api) ~= "table" or api.version ~= 1 then api = nil end

local module
local points = {}
if api then
    module = api:RegisterModule(addonName, "map", {
        title = "Map and routes",
        titleRu = "Карта и маршруты",
        visibility = true,
        changes = true,
        build = "map-local-a",
        buildSource = "manual",
    })
    if module then
        points.refresh = api:RegisterPoint(module, "refresh", {
            title = "Refresh route",
            titleRu = "Обновление маршрута",
            memory = true,
        })
        points.search = api:RegisterPoint(module, "search", {
            title = "Find route",
            titleRu = "Поиск маршрута",
            memory = true,
        })
    end
end

function Bridge.Wrap(key, original)
    local point = points[key]
    if not api or not point then return original end
    return function(...)
        return api:Call(point, original, ...)
    end
end

function Bridge.SetVisible(visible)
    if module then api:SetVisible(module, visible) end
end

function Bridge.Changed(key)
    local point = points[key]
    if point then api:MarkChanged(point) end
end
```

Пример применения в файле, где действительно определены операции карты:

```lua
local _, ns = ...
local Perf = ns.PerfBridge

local function SearchRoute(origin, destination)
    -- Существующая реализация поиска и ее возвращаемые значения.
end
SearchRoute = Perf.Wrap("search", SearchRoute)

local function RefreshRoute(origin, destination)
    return SearchRoute(origin, destination)
end
RefreshRoute = Perf.Wrap("refresh", RefreshRoute)
```

Сначала объявляйте функцию, затем оборачивайте ее один раз. Если другие места уже сохранили ссылку на исходную функцию, они продолжат обходить обертку. Расположите подключение до сохранения ссылок обработчиками. Не создавайте новую анонимную функцию внутри каждого OnUpdate, события или цикла ради `Call`.

Для события изменения используйте существующую ветку обновления данных:

```lua
if routeDataChanged then
    ns.PerfBridge.Changed("refresh")
end
```

Для видимости передавайте обычный boolean. Например, в уже существующих обработчиках **собственного** окна:

```lua
ns.PerfBridge.SetVisible(not not ownedWindow:IsVisible())
```

Нужен начальный сигнал, а затем обновления при изменении эффективной видимости, включая родителей, если они влияют на окно. Не добавляйте покадровый опрос видимости. Уточните, что значит «видимость» именно для этого модуля: работа кеша может быть нужна и при скрытом окне. `nil` означает, что текущее состояние неизвестно.

### Самый дешевый счетчик

Счетчик не оборачивает функцию и не измеряет ее время. Зарегистрируйте отдельную точку с `kind = "counter"` один раз:

```lua
local tickPoint
if api and module then
    tickPoint = api:RegisterPoint(module, "refresh_requested", {
        kind = "counter",
        title = "Refresh requests",
        titleRu = "Запросы обновления",
    })
end

-- В месте события; api и tickPoint кэшируются вне этого обработчика.
if tickPoint then api:Count(tickPoint) end
```

При отсутствии Perf регистрационный блок пропускается, а переменная точки остается `nil`. Счетчики и вызовы не следует дублировать для одного входа, если вы хотите видеть одно число операций. `Count` принимает только точки `counter`, `Call` измеряет только точки `call`.

## Публичный контракт

| Метод | Аргументы и результат |
| --- | --- |
| `RegisterModule(addonFolder, moduleID, options)` | Возвращает непрозрачный handle или `nil, reason`. Папка до 128 байт, ID до 64: ASCII-буквы, цифры, `_`, `.`, `-`. Регистрация до начала замера. |
| `RegisterPoint(moduleHandle, pointID, options)` | Возвращает непрозрачный handle точки или `nil, reason`. ID уникален внутри модуля; до 64 байт, тот же алфавит. |
| `Call(pointHandle, function, ...)` | Вызывает исходную функцию ровно один раз и возвращает все ее значения, включая промежуточные и хвостовые `nil`. Без активной выбранной точки сразу вызывает функцию. Неизвестный handle также оставляет прямой вызов. |
| `Count(pointHandle)` | Для точки `counter`: учитывает один вход, если точка выбрана и запись активна; возвращает boolean. Без записи возвращает `false`. |
| `IsActive(pointHandle)` | Дешевый boolean: выбранная точка сейчас принимает измерения. Можно использовать перед необязательной диагностической работой. Не вызывает часы, профайлер или форматирование. |
| `SetVisible(moduleHandle, booleanOrNil)` | Обновляет сохраненное состояние модуля; во время записи учитывает переход. Одинаковое значение повторно не считается сигналом. Требует `visibility = true`. Возвращает boolean. |
| `MarkChanged(pointHandle)` | Во время записи увеличивает отдельный счетчик сигналов изменения. Требует `changes = true` у модуля. Возвращает boolean. Не сохраняет изменившиеся данные. |
| `SetBuildLabel(moduleHandle, label, source)` | Вне записи меняет метку кода и ее происхождение. Возвращает `true` либо `false, reason`. Отчеты, которые уже сохранены, не переписываются. |
| `GetCapabilities()` | Возвращает новую небольшую таблицу: `apiVersion`, `count`, `cpu`, `memory`, `memoryNeedsProbe`. Вызывать при настройке, не в частом обработчике. `memory` означает наличие кандидата API; начало записи дополнительно выполняет проверку. |

Handle привязан к этому сеансу Lua. Не изменяйте его, не сериализуйте и не используйте после `/reload`. При повторной регистрации того же ID возвращается прежний handle и строка `existing`; новые options не заменяют старые. Перезапуск Lua создает каталог заново. Изменение подписи кода делайте отдельным `SetBuildLabel`.

`RegisterModule` options:

| Поле | Значение |
| --- | --- |
| `title`, `titleRu` | Английское имя и необязательное русское имя, до 120 байт. При отсутствии title используется ID. |
| `visibility` | `true`, если модуль умеет передавать осмысленную видимость. По умолчанию `false`. |
| `changes` | `true`, если автор будет явно вызывать `MarkChanged`. По умолчанию `false`. |
| `build`, `buildSource` | Метка кода до 80 байт и ее источник до 32 байт. Для A/B нужны оба поля. Примеры источника: `manual`, `git`, `build-tool`; это подписи, Perf не удостоверяет их истинность. |

`RegisterPoint` options:

| Поле | Значение |
| --- | --- |
| `title`, `titleRu` | Названия операции по тем же правилам. |
| `kind` | `call` по умолчанию либо `counter`. |
| `memory` | `true` разрешает отдельное нативное измерение выделений этой `call`-точки. По умолчанию `false`; у `counter` всегда `false`. Разрешение автора не включает сбор автоматически. |

Регистрационный каталог ограничен 64 модулями и 512 точками на сеанс. Полный ключ имеет вид `AddonFolder:moduleID:pointID`. Регистрация не должна зависеть от имен игроков, предметов, юнитов, текущей зоны или каждой новой задачи. Для динамических сущностей используйте один стабильный ID операции.

Ожидаемые причины отказа регистрационных методов: `invalid_id`, `registry_limit`, `busy`; для метки кода также `unknown_module`, `invalid_label`. Они не должны становиться ошибкой игрового аддона: оставьте исходный путь выполнения. Не пытайтесь повторять регистрацию на каждом кадре.

## Ошибки, вложенность и ограничения исполнения

- Активный `Call` использует защищенный Lua-вызов для завершения учета при ошибке. Исходный объект ошибки пробрасывается через `error(value, 0)`, функция не повторяется. Стек traceback может содержать обертку Perf; полную идентичность стека исходному вызову не обещаем.
- Поддерживаются обычные синхронные, незащищенные Lua-функции. Не используйте `Call` вокруг coroutine/yield-путей, защищенных действий, secure handlers или логики, зависящей от отсутствия дополнительного Lua/pcall-кадра. Yield через такой вызов не поддерживается.
- Не направляйте secret values, секретные аргументы/результаты или защищенный игровой код в инструментирование. Perf не пытается раскрывать ограничения клиента. Проверки доступности собственных метрик не делают произвольный чужой путь безопасным.
- Рекурсия и обычные вложенные зарегистрированные вызовы используют 32 заранее созданных слота. Превышение глубины выключает дальнейший сбор, но исходная функция продолжает исполняться. Незарегистрированные вложенные вызовы остаются внутри времени родителя.
- Ручных `Begin`/`End` в v1 нет: забытый `End` после раннего выхода или ошибки не должен ломать следующий замер. Асинхронная задача состоит из отдельных синхронных входов; время ожидания не является CPU этой задачи.
- Не заменяйте глобальные функции Blizzard и сторонних аддонов. Измеряйте собственные известные границы. Не используйте `hooksecurefunc` как универсальный способ измерить длительность.

## Что означают цифры

**Вызовы**: количество входов в выбранную точку. В модуле это сумма входов, включая вложенные, а не число кадров. Счетчик изменений считается отдельно и может отличаться от количества вызовов в любую сторону.

**Включенное время**: в CPU-режиме разность `debugprofilestop` вокруг синхронного вызова; в режиме памяти `elapsedMilliseconds` из `C_AddOnProfiler.MeasureCall`. Это разные методы; их отчеты не смешиваются в A/B. Время содержит неизмеренный вложенный код и часть влияния проб. Включенные времена разных точек нельзя складывать в общий CPU аддона.

**Свое время**: из включенного вычтены только известные вложенные измеренные вызовы. Это не полное эксклюзивное время всего Lua. Невалидные часы, ошибки и неполная вложенность дают недоступное значение. Модульное время суммирует внешние измеренные вызовы этого модуля, чтобы не повторять его вложенную работу. Разные модули все равно могут перекрываться.

**Выделено/освобождено**: байты во время нативного измерения, включая вложенные вызовы. Освобождение может относиться к объектам, созданным раньше или другим кодом. Баланс не равен удерживаемой памяти функции, размеру кеша или утечке. Это не общая ОЗУ процесса. Снимки общей памяти не используются как подмена этих значений.

**Скрытое окно**: только явный сигнал модуля. До первого boolean или после `nil` состояние неизвестно. Неполные сигналы не превращаются в нули. Скрытый модуль может выполнять нужную подготовку или поддерживать кеш. `MarkChanged` не доказывает полезность вызова, а его отсутствие не доказывает бесполезность.

**Нагрузка Perf**: нативный `LastTime` самого аддона и отдельно учтенная служебная работа. Эти оценки могут пересекаться; их нельзя складывать или вычитать из результатов. Первый нативный кадр пропускается, поскольку `LastTime` относится к предшествующему кадру. Среднее служебной части включает вызовы инструмента и контроль активной записи, но не всю цену изменения стека, отрисовки, подготовки и сериализации. Полная цена требует сравнения с тем же сценарием без проб.

В JSON недоступные поля опущены; их отсутствие означает `n/a`, а не ноль. Для времени дополнительно доступны `samples`, `missing`, `errors`, `selfValid`, для памяти `memorySamples`, для видимости `visibilityCalls` и `visibilitySeconds`. Считайте источник и метод частью данных.

## Нагрузка и жизненный цикл

| Состояние | Работа Perf |
| --- | --- |
| Нет Perf / несовместимый API | Адаптер возвращает исходную функцию; регистрация пропущена. |
| Perf есть, запись выключена | У `Call` короткая проверка и прямой вызов. `Count`/`MarkChanged` сразу возвращают false. Нет новых таблиц, строк, часов и покадрового опроса сборщика. Проверка и дополнительный вызов все же имеют ненулевую стоимость. |
| Счетчики / CPU | Числовые агрегаты, заранее выделенные слоты вложенности и кольцо стоимости. Нет таблицы результатов на каждый вызов, аргументы и результаты не сохраняются. |
| CPU + память | Отдельный opt-in; нативный API возвращает таблицу результатов на каждый вызов. Perf ее не сохраняет и не ведет журнал событий. Этот путь дороже. |
| Окно скрыто | Отрисовка остановлена; ограниченная активная запись продолжается. |
| Завершение | Копирование/очистка ограниченного отчета и сохранение в историю. Эта работа вне измеренного интервала. |

Пределы активной записи: 15 секунд по умолчанию, максимум 60; не более 128 выбранных точек, 20 000 суммарных входов/сигналов и 32 уровней вложенности. Один активный сборщик; обычная запись, ожидание боя/босса и разработческая запись взаимоисключающие. Во время нее Perf пропускает собственный фоновый сбор и откладывает сканирование памяти.

Защита останавливает **сбор**, когда учтенная служебная работа превышает 1 мс в среднем за 60 кадров или 20 мс за проход/кадр. Лимит не прерывает выполняемую функцию, не гарантирует FPS и не может остановить зависший игровой код. Завершение отчета происходит после выхода из текущего синхронного вызова, обычно на ближайшем кадре. Ошибка функции, выход, ручная остановка и защитные лимиты дают частичный отчет.

Perf не вызывает принудительный GC, не переключает `scriptProfile`, не отключает аддоны или их таймеры. При отсутствии/некорректном ответе нативного API память остается недоступной. При начале режима памяти Perf проверяет API на безопасной пустой функции, включая возвраты с nil. Реальную операцию нельзя повторять «для проверки» или как fallback после ошибки API.

## Работа с интерфейсом и A/B

Открытие: `/sperf dev` или вкладка «Разработка». «Новый замер» выбирает модули, сценарий, длительность и режим. Во вкладке «Функции» выберите строку и нажмите «Замерить эту точку» для одного участка. У модуля со счетчиками/неподдерживаемыми точками полный режим памяти недоступен; отдельная подходящая call-точка может быть измерена отдельно.

Последние 20 разработческих отчетов хранятся в `Sintezza_PerfDB.developer`, отдельно от существующей истории. Кнопка выбора отчета не включает запись. `A`/`B` назначают выбранный отчет; повторное нажатие снимает назначение. «Снять A/B» сохраняет сами отчеты. Назначение группы не защищает от лимита истории: экспортируйте важное сравнение. Удаление отчета требует подтверждения. `/sperf stop` останавливает также разработческую запись.

Для сравнения:

1. Вариант A: метка кода, например `map-local-a`, источник `manual`; три полные записи одинакового сценария и длительности.
2. Внесите изменение в аддон и поменяйте только метку кода на `map-local-b`. Релизную версию ради этого не повышайте.
3. Вариант B: три повтора с тем же набором точек, режимом, клиентом, зоной/инстансом, группой, состоянием боя и лимитом FPS.
4. Назначьте отчеты группам, выберите интересующую точку и откройте «Регрессии». Смотрите число повторений, медианы и стоимость наблюдателя.
5. Подтвердите эффект обычным замером без активных разработческих проб. Улучшение участка не равно такому же улучшению FPS.

Проценты скрываются для неполных записей, ошибок/пропусков, неизвестных или изменившихся условий, разных методов/точек, отсутствующих меток кода и смешанных сборок внутри одной группы. Сравниваются одинаковые заданные длительности; расхождение фактических допускается до большей из величин 0,5 секунды или 2% меньшей длительности. Различие кода между A и B ожидаемо; внутри одной группы код должен иметь одинаковую метку и источник. Ручная метка не доказывает состав файлов, одинаковая версия не доказывает одинаковый код.

## Чеклист для задачи Sintezza_UI

## Источник API и границы проверки

Forever 1.60.1 (70938), interface 16001: [декларация AddOnProfiler на закрепленном коммите](https://github.com/Gethe/wow-ui-source/blob/bebcb6bf309cf41b41bd74f8ca651e6a105b2676/Interface/AddOns/Blizzard_APIDocumentationGenerated/AddOnProfilerDocumentation.lua). `MeasureCall(func, ...)` возвращает `AddOnProfilerCallResults`, затем исходные возвращаемые значения; аннотация секретных аргументов `AllowedWhenUntainted` не является разрешением инструментировать любой контекст.

Текущая реализация принимает только доступные конечные числовые метрики. Значения выделений больше безопасного целого `2^53 - 1` и иное представление BigUInteger отвергаются, чтобы не выдавать потерю точности за измерение. Исходные результаты функции при некорректных метриках сохраняются; сбор завершается частичным отчетом.

Lua-моки проверяют наш контракт и ограничения. Они не доказывают стоимость, семантику нативного профайлера, безопасность произвольных пользовательских функций или внешний вид в игре. Текущий статус проверок находится в [Phase3.md](Phase3.md), команда запуска в [Tests/README.md](../Tests/README.md).

## English integration summary

Add `Sintezza_Perf` to the adopter's existing **OptionalDeps**, then load its bridge before instrumented code. Require `_G.Sintezza_PerfAPI.version == 1`. Register modules and stable call/counter points once; keep handles in session-local variables. `Call(point, fn, ...)` forwards all return values and propagates the original error object without retrying. `Count` is for counter points; `SetVisible` and `MarkChanged` are explicit signals. The full Lua adapter above returns the original function when Perf is absent, so no hard dependency is introduced.

Instrument only your own synchronous, unprotected, non-yielding code with ordinary non-secret arguments. Wrap once, never per event/frame. Native memory measurement is opt-in, probed and more expensive; unavailable data is not zero. CPU/inclusive times overlap; known self time subtracts only measured children. Allocation balance does not prove a leak. A hidden window may still do useful work.

Use `/sperf dev` to record modules or a single selected point, choose saved reports and assign A/B. Code labels are independent of release versions; labels and their source are required for regression comparison. The API version, methods, limits, fields and reason strings in the tables above are stable English identifiers. Developer reports use a separate bounded store; no Sintezza_UI integration is installed by Perf itself.
